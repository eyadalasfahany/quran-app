# 0060 — Taybah-generated recitation timings

Date: 2026-11-04 · Status: accepted (developer, 4 Nov 2026) · Amends ADR 0052 by adding an override layer: a Taybah timing, where one exists for a surah file, is used instead of QF's. ADR 0052's untrusted list, its decisions 1 to 3 and the device checks are unchanged. Amends spec §12 "Timings must match the audio". Rests on ADR 0008, 0022, 0023, 0037, 0039, 0040, 0044 (packs build at web start), 0052. Plan: `docs/plans/recitation-timings.md`.

## Context

ADR 0052 stopped the app from highlighting four QF chapter reciters whose QF timings do not match their audio: 5 (Hani ar-Rifai), 158 (Abdullah Ali Jabir), 168 (al-Minshawi with kids) and 174 (Yasser ad-Dussary). They play with «بدون تتبع». Decision 2 of that ADR: no audio analysis on the server (no `ffmpeg`).

A local, offline tool (`tools/recitation-align/`, Python) now produces per-word timings for a surah audio file against the Tanzil text, by CTC forced alignment with a wav2vec2 Arabic model (Apache-2.0). On one file (surah 59, Islam Sobhi) it aligned 24 of 24 ayahs and 451 words in about 3 minutes of CPU on an M1 Pro. The plan uses it to give the four reciters timings that match the exact file that plays.

## Decision

1. **Nothing runs on Railway except an import.** No model, no audio and no analysis on the server (ADR 0052 decision 2; single replica with a volume, ADR 0022 and 0040). The tool runs on the developer's machine. Only its output ships.
2. **Output ships as committed derived data.** One minified JSON file per recitation and surah under `apps/api/resources/recitation-timings/`, in the manner of `apps/api/resources/azkar/audio/hisn-0.0.2.manifest.json`. An artisan command imports it at web start, before `content:ensure-packs`, like packs (ADR 0044). It is idempotent: it stores a digest of each file and changes nothing, and bumps no version, when the digest is unchanged.
3. **Timing is made against the exact file that plays.** The tool downloads `chapter_audio_files.audio_url` as stored, and records the URL, byte size, sha256 and measured duration (never `duration_ms`, which ADR 0052 found wrong by up to an hour) with the timings. The import skips any file whose current `audio_url` differs from the recorded one.
4. **Separate tables, not a `source` column.** Taybah rows live in `taybah_recitation_timings` (key: `recitation_id`, `chapter_id`, `verse_id`) with one provenance row per surah in `taybah_timing_sets` (audio URL, bytes, sha256, measured duration, tool version, model revisions, digest). Neither table has a foreign key to `chapter_audio_files`. Reason: `ChapterRecitationsHandler::replaceFromSnapshot` calls `files->deleteForRecitation()` and re-inserts the files (line 137), and `recitation_timings.audio_file_id` is `cascadeOnDelete()` (migration `2026_10_27_143840_create_recitation_timings_table.php`), so every QF snapshot would delete any row in `recitation_timings`, whatever column it carries. A QF `audio_segment` row mutation with the same primary key would also find and delete it (`skipRow` → `rowExists` → `removeRow`, lines 195–222). The pack and device primary key `(audio_file_id, verse_id)` (`PackSchema::recitationTimings`, spec §6) cannot hold a source. With separate tables the QF handler never sees Taybah rows, and the importer never touches QF rows.
5. **Packs and devices see one table, with Taybah as an override.** For each surah file, the pack snapshot (`PackBuilder` reads rows through `snapshots->eachChunk`, line 125) fills `recitation_timings` from `taybah_recitation_timings` when a Taybah set exists for that file: the set is joined to the current `chapter_audio_files` row on recitation and chapter and on `audio_url`. Where no Taybah set exists, nothing changes: a trusted QF reciter keeps QF's rows, and a reciter in `quran.untrusted_timing_recitations` has none and plays without highlight. A file whose URL changed loses its Taybah rows and falls back the same way. The device schema, `timingsFor`, `timingsFitAudio` and the pack schema do not change.
6. **The untrusted list keeps its ADR 0052 meaning.** It still says "QF's timings for this reciter are not trusted": the handler never stores their `audio_segment` rows (ADR 0052 decision 1) and a reciter leaves the list only by the route ADR 0052 gives (QF publishes timings that match, the developer decides). Taybah timings are an override on top, per surah file, never a reason to remove the reciter, and never a way to restore QF rows. `has_word_segments` for a recitation is true when any file in its pack has segments, from QF rows or from Taybah rows.
7. **Reaching devices.** The import changes the resource version and `changes_floor_version` together, deletes the resource's `content_changes`, and dispatches `ResourceContentChanged`, as the ADR 0052 migration does, so installed devices replace the pack. It does this only when a digest changed.
8. **Ayah rows follow QF's convention.** Ayah 1 starts at 0 and any audible basmala falls inside its span with no word segment (checked on 3 Nov 2026 across QF reciters: for the files where word 1 starts at about 5–10 s, ayah 1 still starts at 0). Rows are contiguous, each ayah ending where the next starts, and the last ayah ends at the measured duration. Word segments use QF word positions, not Tanzil token positions (plan, "Word positions"). An ayah the tool cannot place with confidence gets ayah timing and `segments` null. A file below the surah-level floor is not shipped (the surah plays without highlight, as today).
9. **Accuracy gate before any reciter ships.** The tool is run on a trusted reciter (Mishary al-Afasy, QF 7) and compared with QF's rows, then on the target reciters with ADR 0052's pause-alignment audit. Thresholds are in the plan. Listening is not ground truth.
10. **One Taybah timings path.** The same two tables and the same import serve (A) QF reciters, in the list or not, and (B) the MP3Quran reciters of ADR 0061, whose resources belong to another content source and are never touched by the QF sync (`ContentSyncService.php:71` resolves `sourceId('qf')`, and its reconcile loops take that source id, for example line 413). Override rule: Taybah set for the file wins; otherwise the recitation's own rows (none for a non-QF resource). The audio rights and hosting for (B) are ADR 0061's. Reciter 168 (al-Minshawi with kids) stays out: ADR 0052 decision 3 is unchanged and no Taybah timing is made for it.

## Consequences

- Three QF reciters (5, 158, 174) can regain highlight, word-by-word where confidence allows, with no app code change; the Listen label disappears by itself on a surah that has full coverage, and stays on the surahs left without Taybah timings.
- Repo and image grow by about 2.2 MB per reciter of JSON (plan, "Size").
- A QF file URL change silently removes that surah's Taybah timings from the pack until the tool is rerun. A verify command reports it.
- A monotonic single pass cannot express repeated words. In Afasy's QF rows 991 of 6,236 ayahs repeat positions, so generated rows will have fewer repeats than QF's trusted rows. This costs word accuracy only in those ayahs.
- **Dependency rule exemption (developer, 4 Nov 2026).** The two dev-only models, `tarteel-ai/whisper-base-ar-quran` and `jonatasgrosman/wav2vec2-large-xlsr-53-arabic` (both Apache-2.0, last updated December 2022, pinned revisions in `tools/recitation-align/recitation_align/models.py`), are exempt from the 12-month rule because the tool is dev-only and never shipped. The exemption covers these two models only. The content plan's version table records it.
- MP3Quran's own published ayah timings (115 readings, ayah level only) and the aligner's output go through the same import and the same accuracy gate (plan, step 6). MP3Quran's ayah 1 can start after a basmala (read 123, surah 59: ayah 1 at 6,100 ms), so the importer rewrites ayah 1 to start at 0 and records the original start in the set row.
- Open for the developer (track A only; MP3Quran is covered by ADR 0061): QuranicAudio's site says personal use only (`docs/content-plan.md` line 140), and ADR 0008 lets the app play QF's links under QF's terms. Whether we may publish timings derived from analysing those files is not decided here; it blocks shipping track A, not building it.
- Reciter 168: no highlight at all, unchanged (developer, 4 Nov 2026). Out of scope.
- **Decisions of 4 Nov 2026.** Accuracy thresholds as proposed in the plan (step A6). A reciter ships only when complete; no surah-by-surah shipping. The 21 verses whose QF word count the position rules do not match get ayah-level highlight only (`segments` null); no hand-written merge table. Still open: whether QuranicAudio-derived timings may be published (blocks shipping track A).

## Amendment, 5 Nov 2026

A QF `audio_segment` row mutation for a surah file that a Taybah timing set owns (a `taybah_timing_sets` row matching the file's recitation, chapter and current `audio_url`) is stored as the QF fallback row but emits no content change: no change row and no version bump. Devices therefore keep the Taybah rows instead of receiving a QF row that would overwrite them. For a file with no matching set nothing changes. Brief: `docs/plans/recitation-timings/api-step-03-handler-flag.md`. The committed folder is `apps/api/resources/recitation-timings/` (decision 2 stands).
